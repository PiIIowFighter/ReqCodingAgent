# 项目迭代与提交策略

> 版本：1.1
>
> 生效日期：2026-08-28
>
> 适用范围：三个功能迭代及其全部设计、实现、测试和实验

## 1. 功能迭代

项目采用三轮功能迭代：

1. 迭代一：建立可复现、可追溯、能够自动判定补丁质量的评测环境。
2. 迭代二：实现完整可用的基础 Coding Agent，并完成冻结配置下的 E1／E2。
3. 迭代三：加入静态编码的需求澄清特色能力，并完成冻结配置下的 E3／E4。

功能迭代与 Git 提交不是一一对应关系。每轮允许包含多个提交；一轮是否完成由该轮验收标准和审计证据决定，而不是由某一个固定提交决定。

## 2. Git 提交纪律

- 每个提交必须对应一个可解释的设计、实现、测试、缺陷修复、配置冻结或实验结果。
- 不为增加提交数量制造空提交，不虚假拆分同一原子变更。
- 不伪造开发顺序，不回填虚假日志，不把未运行项目描述为已通过。
- 每次提交前运行与变更范围对应的测试，并将真实结果保存到运行证据目录。
- 中间提交可以明确说明某轮仍在建设中；只有满足该轮全部验收标准后才能标记完成。
- 每次提交后执行普通 push。已推送历史不得 rebase、squash、amend、force push、删除或以其他方式改写。
- 若推送失败，保留本地提交并报告；不得通过改写历史绕过问题。

## 3. 不可覆盖的运行证据

所有用于设计决策、提交验收或正式测评的重要运行都必须保存。完整原始产物使用：

- `artifacts/runs/iteration1/<run_id>/`
- `artifacts/runs/iteration2/<run_id>/`
- `artifacts/runs/iteration3/<run_id>/`

相应可提交脱敏证据使用：

- `audit/iteration1/runs/<run_id>/`
- `audit/iteration2/runs/<run_id>/`
- `audit/iteration3/runs/<run_id>/`

`run_id` 由 UTC 时间、运行类型和短配置哈希组成，不得覆盖已有目录。完整产物至少保存运行清单、配置快照、事件流、标准输出、标准错误、结果、校验和及 COMPLETE／FAILED 标记。audit 由真实原始产物自动脱敏生成，不得手工伪造通过状态，不得包含 API Key、SSH 信息、完整环境变量、用户绝对路径或大段原始日志。

每轮 `audit/iterationN/index.json` 采用追加式索引。旧结果只能保留或显式标记失效，不能静默删除。原始 artifacts 由 Git 忽略但须在本机持续保留。

## 4. 迭代一纪律

no-op／gold 属于评测环境验证。发现实现、基础设施或测试问题后可以修复并重新运行，但必须保留旧日志、旧结果、状态和修复原因，不得覆盖。迭代一按规范 1.3 的资源感知门槛验收：15 题静态数据校验、`pytest -m "not integration"` 默认快速测试、一次真实 Agent/evaluator 隔离证明、开发题 `django__django-11133` 的 no-op 与 gold 各一次，以及脱敏的 1×2 smoke 摘要。原 15×2 replay 和 `validate-all` 保留为 optional full profile，不再是迭代一完成或开始迭代二的前置条件。

## 5. 迭代二纪律

迭代二可根据单元测试、集成测试和 3 个 dev 配对样本多轮调整。每个重要版本使用 `v001`、`v002` 等稳定递增编号，保存：

- 完整配置及配置哈希；
- 开发集结果；
- 发现的问题；
- 对应代码或提示词修改；
- 接受或回滚决定。

E1／E2 开始前必须提交并冻结基础 Agent 配置及其哈希。12 个 test 任务的正式结果不得用于继续调整基础 Agent。

若正式运行发现基础设施或 evaluator 缺陷，应将原运行显式标记为 `invalid`，记录证据、缺陷和影响范围；修复后对全部受影响实验单元统一重跑，不能只重跑失败题。

候选补丁未通过官方测试、Agent 超时或没有生成补丁均属于真实实验结果，不能因此重跑或调参。

## 6. 迭代三纪律

迭代三只在 dev 样本上调整需求澄清能力。每个重要版本沿用稳定编号、配置哈希、开发结果、问题和接受／回滚记录。冻结澄清配置后再运行 E3／E4；test 正式结果不得用于继续调整。

发现基础设施或 evaluator 缺陷时，沿用迭代二的 `invalid` 标记、影响分析和统一重跑规则。真实的未解决、超时、无补丁和错误澄清结果不得通过选择性重跑消除。

## 7. 可审计性

代码提交、配置冻结、运行证据和 audit 索引共同构成开发历史。任何结论必须能追溯到具体 commit、配置哈希和 run_id。若证据不足，只能报告未完成或阻塞，不得推断为通过。
