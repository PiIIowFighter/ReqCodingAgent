## 1. 文档用途

本文档是第一次迭代的唯一实施基线，供 Claude Code 在项目根目录中完成评测环境。除修复明确的事实错误外，不得在实现过程中自行更换数据、改变模糊化文本、调整评分口径或提前实现第二、三次迭代。

本项目采用三轮功能迭代；功能迭代与 Git 提交不是一一对应关系，每轮允许包含多个真实、职责单一且有验证证据的提交：

1. 迭代一：建立可复现、可追溯、能够自动判定补丁质量的评测环境。
2. 迭代二：实现完整可用的基础 Coding Agent，并在冻结评测集上完成 E1／E2。
3. 迭代三：加入静态编码的需求澄清特色能力，并完成 E3／E4。

本文档只授权实现迭代一。迭代二、三的信息仅用于保证数据结构前向兼容。全局提交与实验纪律见《项目迭代与提交策略.md》。

## 2. 原始考核约束

最终项目需要独立实现一个简化的 Claude Code／Codex 类 Coding Agent，不能调用现成 Agent 框架或 Agent SDK。历史与上下文管理、工具调用、输出解析、循环终止和错误处理均需自行实现。

同时遵守原题要求：

- 使用题目发布后新建的公开 GitHub 或 Gitee 仓库并保留完整提交历史，不得压缩或改写已经推送的历史。

- 最终演示视频不超过 2 分钟，采用 MP4 格式且不超过 200 MB。
- 最终提交一个以本人姓名命名的 ZIP，仅包含 README.txt 和视频。
- 截止时间为 2026-09-02 24:00，北京时间；截止后不得继续向仓库推送。

第一次迭代不实现 Coding Agent，但必须为后续 Agent 提供可信的外部判分环境。

## 8. 原题与模糊题面的统一规则

### 8.1 官方原题

- 完整版必须逐字使用固定版 Verified 的 problem_statement。
- 不允许翻译、润色、修正拼写、删除代码或加入提示。
- 运行准备脚本时从固定数据版本读取，不手工复制 15 份原文。
- 必须计算并核对第 7 节 SHA-256。

### 8.2 模糊版本

- 模糊强度统一为 medium。
- 每题只改变一个语义因素。
- 信息遗漏：删除一个关键事实的全部直接表达，但保留任务和现象。
- 具体性降低：保留该槽位的存在，但把精确值、接口或格式改成泛化表达。
- 指代歧义：保留相关实体和行为，但取消指代表达与真实目标的明确绑定，使回答前至少存在两种合理解释。
- 未列明的原题内容保持不变；若原题中的代码或标题会直接泄露被隐藏绑定，则按任务条目中明确规定同步替换。
- 生成 fuzzy_prompt 后计算 SHA-256，并在迭代一首次包含冻结数据的提交中冻结。

### 8.3 禁止泄漏

模糊题面和 Oracle 回答只能来自官方 problem_statement。不得从以下内容抽取或添加信息：

- gold patch。
- test patch。
- hints_text。
- 具体源文件位置。
- 可直接转化为补丁的实现提示。

- 保留 foo、bar、baz 全部被显示的现象。
- Expected behavior 改为：autodoc should respect the explicit export list.
- 隐藏类别：trigger。
- 官方证据：No entries should be shown because __all__ is empty.
- Oracle：__all__ 被显式设置为空列表；因此不应显示任何条目。
- acceptable_intents：trigger、expected_behavior。

### 9.3 指代歧义

以下条目使用给定核心文本替换会直接绑定目标的标题、代码摘录和描述；与目标绑定无关的环境信息可以原样保留。

#### T-R1 django__django-13933

- 核心文本：ModelChoiceField and ModelMultipleChoiceField report invalid choices inconsistently: one includes the rejected value, while the other only says that the choice is unavailable. Make the field include this value in the invalid_choice error and its parameters.
- 歧义：“该字段”可能指两个字段中的任意一个。
- 隐藏类别：target。
- 官方证据：Compared with ChoiceField and others, ModelChoiceField does not show the value of the invalid choice when raising a validation error.
- Oracle：需要修改的是 ModelChoiceField。ModelMultipleChoiceField 已经会报告无效值；目标是让 ModelChoiceField 的 invalid_choice 错误也携带该值。
- acceptable_intents：target。

#### T-R2 psf__requests-2317

- 核心文本：Neutronclient passes the request method and other request parameters through safe_encode_list. One of the resulting byte values is then converted by Requests into a literal string with a b'...' prefix, causing a 404 response. Normalize that parameter to the corresponding native string.
- 歧义：“其中一个字节值／该参数”可能指请求方法或其他请求参数。
- 隐藏类别：target。
- 官方证据：method = builtin_str(method) 会把二进制方法值 b'GET' 转为其带 b 前缀的字面字符串。
- Oracle：问题对象是 HTTP 请求方法，例如 b'GET' 应成为原生字符串 GET，而不是字符串 b'GET' 的字面表示。
- acceptable_intents：target、trigger。

#### T-R3 scikit-learn__scikit-learn-13779

- 核心文本：A VotingClassifier contains two base estimators named lr and rf. After one component is set to None, fitting it with sample_weight still attempts to call fit on that object and raises an exception. The disabled component should be ignored correctly.
- 歧义：“拟合它”和“该对象”可能分别指组合分类器、基础估计器或被禁用项。
- 隐藏类别：target。
- 官方证据：Because we don't check for an estimator to be None in sample_weight support, fit is failing；原题复现将 lr 设为 None。
- Oracle：被设为 None 的是 lr。需要处理 VotingClassifier 使用 sample_weight 拟合时对基础估计器进行检查和调用的路径；None 项必须被跳过。
- acceptable_intents：target、scope_constraint。

#### T-R4 sphinx-doc__sphinx-8721

- 核心文本：After configuring viewcode_enable_epub=False and running make html epub, both builders run, but one output still generates viewcode module pages. That builder should not generate these pages, while the other builder should retain its existing behavior.
- 歧义：“其中一个输出／该构建器／另一个构建器”未直接绑定到 HTML 或 EPUB。
- 隐藏类别：target。
- 官方证据：module pages should not be created for epub by default.
- Oracle：应禁止生成 viewcode 模块页面的是 EPUB 输出；HTML 输出仍可正常生成这些页面。
- acceptable_intents：target、scope_constraint。

## 10. 开发集的模糊化与 Oracle

### D-O1 django__django-11133

- 标题：HttpResponse incorrectly serializes some database binary values。
- 正文：When database BinaryField content is written to an HttpResponse, the value returned by SQLite works correctly, but the same content returned by PostgreSQL becomes a representation like b'<... at 0x...>' instead of b'My Content'. String and ordinary bytes inputs both work correctly.
- 删除具体 Python 输入类型及直接构造该类型的代码。
- 隐藏类别：trigger。
- 官方证据：Postgresql returns the contents of the field as a memoryview object.
- Oracle：PostgreSQL 返回的 BinaryField 内容是 memoryview；最小触发输入为 HttpResponse(memoryview(b"My Content"))。
- acceptable_intents：trigger。

### D-S1 scikit-learn__scikit-learn-14983

- 保留 RepeatedKFold、RepeatedStratifiedKFold、repr 调用及带内存地址的错误输出。
- 精确期望替换为：Both objects should display stable, readable constructor-style representations that include their cross-validation configuration, rather than default object addresses.
- 隐藏类别：expected_behavior。
- 官方证据：原题 Expected Results 给出两个默认对象的完整构造器式 repr。
- Oracle：默认输出分别为 RepeatedKFold(n_splits=5, n_repeats=10, random_state=None) 和 RepeatedStratifiedKFold(n_splits=5, n_repeats=10, random_state=None)。
- acceptable_intents：expected_behavior。

### D-R1 matplotlib__matplotlib-25332

- 标题：A figure fails after combining label alignment and serialization。
- 保留 fig.align_labels() 和 pickle.dumps(fig)，删除明确指出触发行的注释。
- 描述：一个包含两个子图的 Figure 依次执行标签对齐和序列化。两个操作组合使用时，其中一个操作使后续流程出现 TypeError: cannot pickle 'weakref.ReferenceType' object。移除它后另一个操作可以成功，组合流程也应正常完成。
- 隐藏类别：trigger。
- 官方证据：Unable to pickle figure after calling align_labels().
- Oracle：触发条件是先调用 fig.align_labels()，随后执行 pickle.dumps(fig)；未调用标签对齐时可以序列化，目标是对齐后仍可序列化。
- acceptable_intents：trigger、target。

## 12. 自动澄清协议的前向兼容要求

第一次迭代不实现澄清，但数据和结果模式需兼容以下冻结协议：

## 13. no-op 与 gold replay

### 13.1 no-op

对每个任务：

1. 在 base_commit 上准备官方测试环境并应用 test patch。
2. 不应用候选补丁。
3. 每个 FAIL_TO_PASS 测试应失败。
4. 每个 PASS_TO_PASS 测试应通过。

### 13.2 gold

对同一任务：

1. 从完全干净的 base_commit 开始。
2. 应用官方 gold patch。
3. 应用官方 test patch。
4. 所有 FAIL_TO_PASS 和 PASS_TO_PASS 测试均应通过。

### 13.3 判定与替换

- 只有 no-op 和 gold 均满足要求，任务才可被冻结。
- 因 Docker、依赖、网络、平台或测试波动失败时，应先分类为基础设施问题并保留完整日志。
- 只有确认环境或测试自身不稳定时才允许提出替换。
- 不得因为基础 Agent 解不出某题而替换。
- 替换必须记录原 ID、候选 ID、原因、日志、时间和人工批准；Claude Code 不得自动决定。

## 14. evaluator 输出

每次 replay 至少保存：

- run_id、case_id、instance_id、split、mode。
- 固定数据与 harness 版本。
- repo、base_commit、Docker image。
- 开始／结束时间和 wall time。
- 环境准备、补丁应用和测试阶段状态。
- 每个 FAIL_TO_PASS／PASS_TO_PASS 的结果。
- 最终状态：passed、test_failed、infra_failed、timeout 或 invalid。
- stdout／stderr 日志位置和错误分类。

汇总至少输出：

- JSON 或 JSONL 机器可读结果。
- 一份简明 Markdown 报告。
- 15 题 no-op／gold 通过矩阵。
- 失败任务及其失败阶段。

运行产物、缓存、镜像和大日志不提交 Git，只提交小型示例或结构定义。

## 15. 后续正式实验和评分口径

本节只冻结接口，不在迭代一运行。

| 实验 | Agent | 题面 | 目的 |
| --- | --- | --- | --- |
| E1 | 第二次迭代基础 Agent | 12 个完整题面 | 基础能力 |
| E2 | 第二次迭代基础 Agent | 12 个模糊题面 | 模糊输入造成的下降 |
| E3 | 第三次迭代澄清 Agent | 12 个模糊题面 | 澄清能力带来的恢复 |
| E4 | 第三次迭代澄清 Agent | 12 个完整题面 | 检查过度澄清与能力回退 |

总计 48 次正式运行。每个单元默认运行一次，固定模型、系统提示词、温度、最大步骤和预算。若时间允许，可从每种模糊类型选一题重复运行稳定性实验，但不得替代主实验。

### 15.1 主指标

Resolved 只有在全部 FAIL_TO_PASS 通过且全部 PASS_TO_PASS 继续通过时取 1，否则取 0。

- 基础成功率：E1 resolved 数／12。
- 模糊下降：E1 成功率减 E2 成功率。
- 澄清增益：E3 成功率减 E2 成功率，为最重要的亮点指标。
- 无回退：比较 E4 与 E1。
- 所有比率同时报告“成功数／12”和百分比。

### 15.2 澄清指标

- hidden-slot hit rate。
- clarification precision。
- 平均澄清轮数。
- 完整题面的 over-clarification。
- clarification-to-resolution。

### 15.3 工程指标

- invalid tool call。
- timeout／loop。
- Agent steps、模型调用次数。
- tokens／cost。
- wall time。
- 修改文件数和补丁行数。

### 15.4 Ragas 定位

- SWE-bench 测试是主判据。
- Ragas 仅作辅助分析。
- Tool Call Accuracy／F1 只用于结构化澄清调用。
- 不对完整 Coding 工具轨迹计算 Tool Call F1，因为代码任务通常不存在唯一正确工具序列。
- Agent Goal Accuracy 和 Topic Adherence 仅作为补充指标。

## 17. 命令与工程要求

建议提供以下 Python 3.11 命令；如适配现有项目名称，README 中必须给出唯一、明确的等价命令：

- python -m evalsys.cli preflight
- python -m evalsys.cli prepare-data
- python -m evalsys.cli validate-data
- pytest -m "not integration"
- python -m evalsys.cli replay --mode noop --split dev --instance-id django__django-11133
- python -m evalsys.cli replay --mode gold --split dev --instance-id django__django-11133
- python -m evalsys.cli smoke-report --noop-run NOOP_RUN --gold-run GOLD_RUN
- python -m evalsys.cli validate-all（optional full profile）
- python -m evalsys.cli report RUN_DIRECTORY（optional full profile）

其中 optional `validate-all` 保留以下完整能力：

1. 版本与依赖预检。
2. 数据下载或缓存校验。
3. 15 对数据的模式、哈希、分布和配对校验。
4. no-op replay。
5. gold replay。
6. 结果聚合。

其他工程要求：

- 支持中断后恢复，已完成且输入哈希一致的任务可以复用。
- 每个任务可配置超时；超时必须分类，不能伪装为测试失败。
- 默认串行或低并发，允许显式配置并发，避免 Docker 资源耗尽。
- 所有 subprocess 使用参数数组并检查返回码。
- 不记录 token、密码、私有路径内容或其他秘密。
- 使用环境变量传入可选凭据，提供 .env.example，但不得提交 .env。
- 错误必须给出可操作信息，不能只输出 Python traceback。

### 17.1 远程仓库与推送流程

1. 实现前检查 git status、当前分支、git remote -v 和 git ls-remote origin。
2. 如果尚未初始化 Git，在项目根目录初始化；不得在子目录创建仓库。
3. 如果 origin 不存在，将其设置为 git@github.com:PiIIowFighter/ReqCodingAgent.git；如果已等价指向该仓库则保持不变。
4. 远程为空时，以 main 作为默认分支；远程非空或本地已有历史不一致时停止并报告。
5. 不把“资料”加入暂存区；只暂存第一次迭代源码、测试、公共审计摘要、README.txt 和本实施规范。
6. 达到内部一致且有对应测试证据的检查点后，可以创建职责单一的中间提交；中间提交不得声称迭代一已经完成。
7. 每次提交前运行与范围相对应的测试并保存运行证据；提交后执行普通 push，首次使用 `git push -u origin main`，后续使用 `git push`。
8. 第 19 节是迭代一完成门槛；15×2 replay 与 `validate-all` 是 optional full profile，不阻塞完成。
9. 禁止 force push、rebase、squash 或 amend 已推送历史，禁止删除远程分支。
10. 每次推送后使用 `git ls-remote origin refs/heads/main` 核对远程提交与本地 HEAD 完全一致。
11. SSH 认证失败时保留本地提交并报告，不得读取、复制、输出或修改用户私钥。

### 17.2 不可覆盖的运行证据与可远程审计结果

所有用于设计决策、提交验收或正式测评的重要运行都必须生成不可覆盖的证据。run_id 由 UTC 时间、运行类型和短配置哈希组成；同名目录已存在时必须拒绝写入，不能覆盖。

完整原始产物保存到 `artifacts/runs/iteration1/<run_id>/`，至少包含 `run-manifest.json`、`config.snapshot.json`、`events.jsonl`、`stdout.log`、`stderr.log`、`result.json`、`checksums.sha256` 及 `COMPLETE` 或 `FAILED` 标记。`artifacts` 由 Git 忽略，但必须在本机持续保留。

每次重要运行同时从真实原始产物自动生成 `audit/iteration1/runs/<run_id>/` 下的脱敏证据，至少包含 `summary.json`、`command.txt`、`config-summary.json`、`result-summary.json`、`log-index.json`、`checksums.sha256`，必要时增加 `matrix.md` 或 `failure-summary.md`。

`audit/iteration1/index.json` 维护全部已记录运行的追加式索引，包含运行类型、状态、配置哈希、原始产物项目相对位置和审计目录。旧结果只能保留或显式标记失效，不能静默删除。至少记录 `unit_tests`、`preflight`、`validate_data`、`replay_noop`、`replay_gold` 和 `validate_all`。

audit/iteration1 至少提交以下脱敏文件，具体文件名可等价调整：

- validation-summary.json：工具版本、固定提交、总状态、开始结束时间和统计。
- noop-gold-matrix.md：15 个 instance_id 的 no-op／gold 结果及失败阶段。
- run-manifest.json：每次 replay 的输入哈希、结果文件哈希和运行状态。
- test-summary.txt：单元测试与 validate-all 的命令和结果摘要。

这些文件不得包含 API key、SSH 信息、用户绝对路径、完整环境变量或大段原始日志。完整日志保存在本地 artifacts 中；审计发现异常时再按任务单独提供。

## 21. 面向教师的简洁说明

本项目没有自行编造代码题和答案。底层任务来自人工验证的 SWE-bench Verified，并进一步限制在 SWE-bench Lite 及人工难度小于 15 分钟的任务中。每题保持相同仓库、base commit 和官方测试，只把完整问题描述改写为一个单因素模糊版本。基础版本和官方补丁分别通过 no-op／gold replay 验证环境有效。后续使用同一任务的完整／模糊配对差异衡量信息缺失的影响，再用澄清 Agent 衡量恢复程度，因此比较对象和判分条件保持一致。
